# x402-compatible agent payments (SRCT adapter)

SRCT speaks the x402 challenge/response shape without a second payment system.
A client calls a paid resource, gets `402 Payment Required` + `PAYMENT-REQUIRED`,
retries with `PAYMENT-SIGNATURE`, and gets `200` + `PAYMENT-RESPONSE`.

```
Agent ──GET /v1/paid/weather──▶ 402 + PAYMENT-REQUIRED (accepts: exact, srct:mini, 500 sat)
Agent ──budget check (max, allow-lists)──▶ PaymentRequest → Authorization → MachinePayment
Agent ──GET + PAYMENT-SIGNATURE──▶ verify → payment_submit → 200 + PAYMENT-RESPONSE + weather
```

## Mapping

- `scheme`: always `exact` (fixed price). `upto` maps to
  `PaymentRequest.max_amount_sat` in the future; refused until a
  settlement-override rule is locked.
- `network`: CAIP-2 `srct:<reference>` where `srct/testnet` ↔ `srct:testnet`
  (`srct_core::x402::srct_network_caip2` / `parse_srct_network`).
- `amount`: decimal satoshi string (x402 atomic units).
- `payload`: the exact `POST /v1/payment/submit` envelope
  (`payment_hex`, `authorization_hex`, `auth_sigs_hex`, `auth_keys_hex`),
  so verification reuses `service::admit_payment` + the node-local
  `CreditBook`. No consensus change.
- Client budget (`X402Budget { max_amount_sat, allowed_recipients,
  allowed_services }`) is enforced *before* signing. A server asking for more
  is refused locally.

## Endpoints (`srct-node`)

- `GET /v1/paid/weather` — demo paid resource (500 sat, recipient `[0x42;20]`,
  service `x402-weather-v1`). Missing signature → `402` + `PAYMENT-REQUIRED`
  header + JSON body. Valid signature → admits the payment, `200` +
  `PAYMENT-RESPONSE` + `{"report": {"weather": "sunny", ...}}`.
- `POST /v1/x402/verify` — facilitator verify (offline checks, no state change).
  Body: `{payment_hex, authorization_hex, auth_sigs_hex, auth_keys_hex}`.
- `POST /v1/x402/settle` — facilitator settle (same admission as
  `POST /v1/payment/submit`). Same body, returns
  `{success, payment_id, payment_response}`.

## Live flow (curl)

```bash
# 1. Challenge.
curl -i http://127.0.0.1:PORT/v1/paid/weather
# → 402 + payment-required: eyJ4NDAyVmVyc2lvbi...

# 2. Agent signs (Rust: build_signed_request → authorize_request →
#    build_signed_payment; see crates/srct-core/tests/x402.rs).

# 3. Verify (optional).
curl -X POST http://127.0.0.1:PORT/v1/x402/verify \
  -H 'Content-Type: application/json' \
  -d '{"payment_hex":"...","authorization_hex":"...","auth_sigs_hex":"...","auth_keys_hex":"..."}'

# 4. Retry with payment.
curl -i http://127.0.0.1:PORT/v1/paid/weather \
  -H 'PAYMENT-SIGNATURE: eyJ4NDAyVmVyc2lvbi...'
# → 200 + payment-response: ... + {"report":{"weather":"sunny",...}}
```

## Demos / tests

- `cargo test -p srct-core --test x402` — pure library roundtrip:
  challenge → budget → authorize → pay → admit (the working demo).
- `cargo test -p srct-node --test x402` — real HTTP: 402 → verify → settle →
  retry with `PAYMENT-SIGNATURE` → 200.
- `python sim/x402_paid_api_demo.py` — envelope-level simulation of the same
  auto-retry loop (no keys; signing lives in the Rust wallet).

## Limits

- `exact` only; multi-option `accepts` may advertise EVM/USDC alongside SRCT,
  but the node only settles SRCT options.
- Demo recipient/service are fixed; production should take the operator wallet
  from config and the policy book stays the authorization engine.
- No external facilitator yet; the node *is* the facilitator for SRCT routes.
